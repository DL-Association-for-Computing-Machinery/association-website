# MVP 技术决策与部署边界

## 当前决策

- 产品形态：移动端优先的内容驱动静态站点。
- 内容入口：飞书人工导出或受控同步到仓库，经审核后构建。
- 线上依赖：首版不依赖飞书运行时 API，不在浏览器调用飞书接口。
- 页面能力：首页、介绍、活动、成果、知识/文章、加入我们。
- 搜索能力：首版使用分类、标签和基础筛选，全文搜索后置。
- 部署：保持平台可替换，先完成静态产物、域名和回滚路径，再绑定具体平台。

## 选型原则

1. 优先使用团队已有能力和平台原生能力。
2. 每个新依赖都要说明它解决的实际问题、维护成本和替代方案。
3. 不能为了竞品的 OIDC、SSO 或微服务架构提前引入后端复杂度。
4. 内容筛选和构建检查是最高优先级 seam；先保证不公开错误内容，再扩展页面交互。

## 后续平台边界

OJ 需要独立的执行隔离、资源限制、队列、题库和故障恢复设计；ECPC 需要明确数据来源、刷新频率、排名口径和人工修正流程。两者都不能作为官网 MVP 的隐含依赖。

## 变更门槛

改变静态发布、内容审核边界、身份系统或部署方式前，先创建 GitHub 决策 Issue，记录现状、候选方案、风险、回滚方式和负责人，再修改 Spec 或 ADR。
