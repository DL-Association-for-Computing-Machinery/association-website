# 东华理工大学计算机协会宣传官网 Spec

Status: specification-complete; implementation-paused-by-user

## Problem Statement

协会多年积累的活动、竞赛、培训和知识资料分散在飞书知识库及其他渠道中，校内新生和潜在成员难以快速理解协会、找到近期活动或确认加入方式。协会也缺少一个可持续维护、可公开分享、能沉淀历史成果的统一入口。

## Solution

建设一个移动端优先、内容驱动的协会官网 MVP。首页回答“协会是谁、最近做什么、有哪些竞赛荣誉、为什么加入”；活动与成果页面提供可浏览的历史归档；知识页面只展示经过公开审核的内容；加入页面提供明确的报名/联系入口。需求表中的 OJ 在线评测和 ECPC 榜单托管作为独立阶段规划，避免首版宣传官网与评测执行系统耦合。官网以静态发布为核心，飞书知识库作为内容源，通过人工导出或受控同步进入仓库，再由构建流程发布。

## User Stories

1. 作为首次访问的学生，我想在首页看到协会定位和核心价值，以便判断是否与我的兴趣匹配。
2. 作为新生，我想看到适合零基础和不同年级的参与路径，以便知道从哪里开始。
3. 作为潜在成员，我想看到近期活动、时间、地点和报名入口，以便参加活动。
4. 作为访客，我想浏览协会的活动历史，以便了解协会是否持续运营。
5. 作为访客，我想按活动类型或年份查看内容，以便快速找到相关经历。
6. 作为竞赛爱好者，我想看到算法竞赛、编程竞赛和训练活动介绍，以便选择参与方向。
7. 作为访客，我想看到竞赛获奖和项目成果，以便判断协会的学习氛围与实践水平。
8. 作为成员，我想查看公开的技术分享和学习资料，以便复习或继续学习。
9. 作为访客，我想看到协会成员或指导教师的公开介绍，以便建立信任。
10. 作为访客，我想通过手机正常浏览和操作报名入口，以便在校园场景快速使用。
11. 作为键盘用户，我想用键盘访问导航、卡片和表单，以便不依赖鼠标。
12. 作为使用辅助技术的用户，我想获得有意义的标题层级、替代文本和焦点状态，以便理解页面内容。
13. 作为协会运营者，我想在一个清晰的内容结构中维护活动、成果和文章，以便减少重复编辑。
14. 作为协会运营者，我想区分内部知识和公开内容，以便避免泄露成员隐私或内部流程。
15. 作为内容编辑者，我想从飞书知识库导出内容并保留标题、层级、图片和附件关系，以便减少迁移成本。
16. 作为发布负责人，我想在上线前查看每条公开内容的 AI 自审结论和来源记录，以便控制准确性、版权和隐私风险。
17. 作为运营者，我想看到失效报名链接或缺失图片的构建检查结果，以便在发布前修复。
18. 作为维护者，我想通过仓库版本记录追踪内容变更，以便回滚错误发布。
19. 作为维护者，我想在没有飞书运行时凭证的情况下构建官网，以便降低线上故障和权限风险。
20. 作为协会负责人，我想先上线一个小而完整的版本，再根据访问反馈增加功能，以便控制开发成本。
21. 作为访客，我想在首页首屏看到协会四个全国性竞赛成绩，以便快速了解协会的核心荣誉。
22. 作为竞赛参与者，我想使用 OJ 在线评测题目和提交入口，以便进行训练和比赛。
23. 作为 ECPC 参赛者，我想查看外榜和历届排名，以便了解实时排名与历史成绩。
24. 作为普通注册用户，我想保存训练或浏览相关状态，以便下次继续使用。
25. 作为协会成员，我想访问成员专属训练与资料，以便参与内部活动。
26. 作为管理员，我想管理公开内容、用户角色和榜单数据，以便维护平台秩序。
27. 作为超级管理员，我想管理管理员权限和平台配置，以便控制高风险操作。

## Implementation Decisions

- 产品形态：响应式官网 MVP，首页、协会介绍、活动、成果、知识/文章、加入我们六类页面；首版可不引入登录，登录和角色体系由 OJ/平台阶段承接。
- 内容模型：统一使用 `Activity`、`Achievement`、`Article`、`Person`、`Link` 等公开内容概念；每条内容包含标题、摘要、正文/媒体、日期、标签、来源和公开审核状态。
- 内容边界：用户已授权复用协会知识库素材，AI 自行核验、脱敏和记录依据，无需另设人工内容审核人；仅“可发布/已发布”内容映射为 `public` 并参与构建。仍无法证实的内容暂缓采用，不拖住其他素材。
- 发布链路：飞书人工导出或受控 API 导出 → 内容清洗/映射 → 代码审查与内容审核 → 静态构建 → 部署。
- 飞书接入：首版不在浏览器直接调用飞书 API，不把 App Secret 或访问令牌放进前端。后续同步脚本使用只读权限，失败时保留上一次可发布内容。
- 导航：桌面端使用顶部导航，移动端使用可键盘操作的折叠菜单；所有页面提供清晰的当前页状态和返回路径。
- 视觉：以学校与协会已有品牌素材为准，先建立颜色、字体、间距和卡片等少量设计令牌，避免首版引入大型 UI 组件库。
- 选型：采用 Next.js、React、TypeScript、App Router、Tailwind CSS、pnpm 与 Markdown/MDX 静态主站；Cloudflare 仅是部署候选。
- 设计准备：沿用协会正式 Logo 与真实合照，选定校园技术成果展方向；采用浅底阅读、深蓝主色和少量青色强调。首屏强调定位、行动与荣誉，窄屏不以挤压字号强行容纳全部板块。
- 媒体：图片必须有替代文本、尺寸与来源记录；大图在构建阶段压缩，外部图片链接不作为唯一内容依赖。
- 搜索：首版提供分类、标签和站点内基础筛选；全文搜索留到内容规模证明需要后再加入。
- 部署：部署平台保持可替换，优先选择项目已有或学校可接受的平台；域名、备案、统计和隐私声明作为上线前配置项。
- 最高测试 seam：内容集合到页面渲染的公开内容边界。测试输入包含草稿、公开、脱敏缺失和失效链接，验证只有合格内容进入页面且构建报告可读。
- 阶段边界：RQ-01 与 RQ-03 进入官网 MVP；RQ-02 OJ 与 RQ-04 ECPC 榜单先产出独立技术决策，再决定自建、集成或托管方案。
- 角色模型：需求表提出游客、普通注册用户、协会成员、管理员、超级管理员；首版只实现游客公开访问，其他角色不在静态官网中伪造。
- OJ 约束：评测执行、沙箱、队列、判题数据和作弊防护属于独立高风险系统，必须单独设计和部署。
- 榜单约束：ECPC 外榜和历届排名需要明确数据来源、刷新频率、排名口径和人工修正流程，不能只做一个静态表格。
- 相关项目参考：InkWords 提供内容摄入、来源、审核、版本和巡检方面的参考；load-balanced-online-oj 可作为 OJ 阶段候选实现，但两者都不直接并入官网 MVP。

## Testing Decisions

- 测试外部行为：公开内容筛选、导航与路由、响应式关键布局、键盘可达性、图片替代文本、失效链接检查和构建产物。
- 内容管道测试：给定一组最小内容夹具，验证导入后的字段映射、草稿隔离、缺失必填字段报错和稳定排序。
- 页面测试：验证首页能展示协会定位、近期活动和加入入口；活动/成果详情能从列表进入并支持无数据状态。
- 可访问性检查：至少覆盖标题层级、颜色对比度、焦点可见、表单标签、`alt` 文本、跳过导航和移动端菜单键盘操作。
- 发布检查：执行一次构建、链接检查和静态产物预览；部署平台确定后再补充平台级 smoke test。
- 测试优先级：先覆盖内容边界和构建链路，再覆盖关键页面交互；不为单纯样式常量编写脆弱测试。

## Out of Scope

- 官网 MVP 不做会员登录、权限系统、个人中心、评论、论坛、即时聊天、在线缴费和报名审核后台；这些属于后续平台阶段。
- 官网 MVP 不实现 OJ 判题执行、题库管理、提交队列、评测沙箱和作弊防护。
- 官网 MVP 不承诺 ECPC 实时外榜或历届排名托管；先完成数据模型与技术选型。
- 首版不把飞书作为线上实时 CMS，不承诺自动同步所有知识库页面。
- 首版不公开内部通讯录、私人联系方式、账号密码、签名及未经筛选的完整附件；协会授权素材可以提取、改编和自审使用。
- 首版不承诺微信公众号历史文章的自动抓取；单篇文章可在获得可用浏览器会话/授权后人工研究，仍需版权许可和结构化来源才能进入官网内容。
- 首版不建设复杂全文搜索、推荐算法、多语言版本和个性化统计。
